# Supabase license backend

## Migration

Apply migrations in order using the Supabase CLI or SQL editor. The license schema is isolated from the hospital scheduling sync schema. All five licensing tables have RLS enabled and no client policies; direct access is revoked from anon/authenticated. Edge Functions use the service-role key only server-side.

## Provisioning the first administrator

1. Create the administrator through Supabase Auth.
2. Obtain that user's Auth UUID from the Supabase dashboard.
3. Insert the UUID into license_admins with role 'owner' and active=true using a trusted SQL session.
4. Do not expose service-role credentials to the Android app.

## Signing key setup

Generate an Ed25519 keypair outside the repository and outside the Android app. Store the private PKCS#8 DER bytes as the Supabase Edge Function secret LICENSE_ED25519_PRIVATE_KEY_PKCS8_B64. Store the raw 32-byte public key as LICENSE_ED25519_PUBLIC_KEY_B64. Set LICENSE_SIGNING_KEY_VERSION to a positive integer. The Edge Function writes only the public key to license_signing_keys. Never put the private key in SQL, GitHub, the desktop, or the admin APK.

The C# verifier expects the raw 32-byte public key under the same key version. The production release must embed this public key or load it from a signed, pinned key-ring update. No production key is generated by this repository.

## Edge Function

Deploy issue-license with JWT verification enabled. It requires an authenticated user whose license_admins row is active and has role owner or issuer. It accepts only activation request QR payloads and a license term. The server claims each request atomically and refuses already-issued request IDs/nonces.

## Operational notes

- The ten-character serial is a lookup/reference, not an authentication secret.
- Revocation is recorded server-side and cannot take effect on a fully offline machine until it reconnects.
- Back up the private signing key in a controlled KMS/secret-management system with access logging and recovery procedures.
- Key rotation: add a new key version, ship the new public key in a desktop release, and only then sign new licenses with that version. Keep old public keys available for existing licenses.
